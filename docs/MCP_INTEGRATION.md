# MCP / Userscripts integration — v0.2 developer handoff

## Current state (2026-10-09)

Implementation is **locally tested, not deployed and not iPad/provider accepted**.

- Backend: Node 22 built-in HTTP, single-device, in-memory command queue (`gateway/server.mjs`). Compatible MCP Streamable HTTP endpoint at `/mcp`, using `2025-11-25` protocol version for broad client compatibility.
- Browser: separate `scripts/safari-ai-agent-remote.user.js`, opt-in Userscripts script using `@inject-into content` and granted `GM.getValue`, `GM.setValue`, `GM.xmlHttpRequest`. Keep original manual script installed separately; **only use remote script on non-sensitive test sites until reviewed**.
- Gateway has **distinct credentials** for the MCP client and iPad. These are generated by the operator, never committed. HTTPS must be provided by a trusted reverse proxy or hosting platform. Server defaults to loopback and requires explicit opt-in to bind behind a proxy.
- Allowed origins must be explicitly set on the gateway. The remote adapter further requires an explicit site opt-in and local approval before each click/navigation; form submissions and consequential buttons are blocked.
- No general-purpose policy language or capability-lease harness is included. That remains a separate later milestone.
- No mandatory Mac model or paid inference API. **Claude remote MCP is the first supported integration candidate**; user-specific subscription/tool availability remains to be checked.

## Generate secrets (run on trusted server, do not paste into chat)

```sh
node -e 'console.log(require("node:crypto").randomBytes(32).toString("hex"))'
```

Run twice to create **different** 64-character hex strings. The first is the **MCP caller secret** entered in the Claude connector configuration. The second is the **device secret** entered only in the iPad Userscripts Remote UI. Never reuse them.

## Local gateway startup (development)

```sh
export MCP_CLIENT_TOKEN='<random caller token>'
export DEVICE_TOKEN='<different random device token>'
export SAFARI_ALLOWED_ORIGINS='https://test-website.example'
export BIND_ADDRESS='127.0.0.1'
export PORT='8787'
node gateway/server.mjs
```

Replace the placeholder domain with the **exact** origin of the harmless test site, no trailing `/` or path. Secrets must be real values, not the angle-bracket examples above. Local startup only tests the server; Claude cannot reach `127.0.0.1` on your Mac.

For Claude mobile: deploy to a trusted public **HTTPS endpoint** with the application listening behind HTTPS termination. Configure `BIND_ADDRESS=0.0.0.0` and `ALLOW_PROXY_BIND=true` **only** inside an isolated hosting environment that requires HTTPS on ingress, forwards `Authorization` unchanged and does not expose the plain HTTP upstream. Keep the service private to the operator; the static bearer model is a single-user MVP compromise, not enterprise OAuth. Persistent storage, reverse-proxy hardening, IP/rate limits, observability, DDoS protection and multi-tenancy would be required before broader public deployment.

## iPad setup

1. Keep **Browser Lab 0.1.1** separate, or disable it on the specific testing site so the buttons do not overlap.
2. Install [Remote Userscript](../scripts/safari-ai-agent-remote.user.js) via its raw `.user.js` URL from the GitHub repository, or save it in the Userscripts directory.
3. Visit your approved non-sensitive test site; allow Userscripts access. Tap **Remote AI**.
4. Enter the base HTTPS gateway URL (for example, `https://gateway.example`; **do not** append `/mcp` or `/device`).
5. Enter the **device secret**, tap Save, then Connect. This is extension-managed storage; do not enter it into the webpage or an AI chat.
6. Keep this Safari tab foregrounded during a workflow. Same-origin navigation can automatically resume the bridge if the script reloads. Cross-site navigation and remote form submission are intentionally disabled in this version.
7. When done, tap **Stop**. Also revoke or rotate both secrets on the server if lost.

## Claude connector setup (requires user sign-in)

Anthropic's official custom remote MCP connectors can be added from Claude's `Customize > Connectors` settings, typically via Claude's web interface. Remote connectors configured on the account can be used by supported Claude mobile apps. Connector availability must be checked with the actual subscription.

1. Add a custom web connector named `Safari AI Agent` pointing to `https://your-gateway.example/mcp`.
2. Choose `No sign in` **only when also configuring an authentication request header**. Set fixed header `Authorization: Bearer <MCP_CLIENT_TOKEN>` as supported by Claude's custom header configuration. Do not publish the secret or put it in the user's prompt.
3. Enable that connector in the chosen Claude conversation on iPad.
4. Ask Claude to use `browser_status`, then `browser_inspect`. Once a real page snapshot is returned, request a harmless fill and a locally approved click. Finish with `browser_verify`.
5. If the actual Claude client does not accept or send fixed authorization headers, stop and document the problem rather than weakening authentication. OAuth would be the preferred replacement.

Official docs: https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp

## MCP commands

| Tool | Behavior |
|---|---|
| `browser_status` | Gateway connectivity/session status |
| `browser_inspect` | Snapshot active tab, refs, visible text and controls |
| `browser_fill` | Fill inspected ref with validated string |
| `browser_click` | Locally approved click of low-impact control only; output is `dispatched`, not verified |
| `browser_navigate` | Locally approved same-origin HTTP(S) destination; caller must inspect next page to verify |
| `browser_verify` | Check visible page excerpt/URL contains expected text |
| `browser_cancel` | Cancel queued MCP calls; in-flight local actions are not automatically rolled back |

Tool output is JSON inside a text content block. Action outcome can be uncertain after navigation or timeout: **do not assume success and do not retry a potentially consequential action**. Inspect state again.

## Security and known limitations

- **Prototype, not a production security boundary.** The browser page is potentially malicious and can influence DOM content, labels, and link destinations; there is no unrestricted script execution feature.
- Credentials should be kept in the Userscripts isolated content context/GM storage; compatibility and leakage resistance must be verified on real Safari. Do not install an `@inject-into page` variant for remote use.
- Model providers receive selected website content when browser_inspect is used. The user must choose what to expose; browser snapshots can contain confidential rendered text even when password values are omitted.
- Only a single active device/origin supported. Multiple Safari tabs on the same origin can compete; users must run one active tab.
- Server queue and session state are **in-memory**, and server restart cancels ongoing commands. After reload, the model must inspect again.
- Userscripts may suspend while iPad is backgrounded. Remote calls time out rather than silently running forever.
- Browser-protected UI, cross-origin iframes, canvas controls, and websites requiring trusted physical input will be unavailable or unreliable.
- A page can change between inspection and execution. The current DOM reference design requires re-inspection after page changes and blocks missing/hidden targets, but not every possible race. Full mutation-version binding is future hardening.
- No remote form submission, file uploads, credential reading, external-domain navigation, multi-user auth, or unattended operation.
- **Provider eligibility, hosted endpoint deployment, end-to-end iPad Safari tests and Claude tool invocation are still pending and are release blockers.**

## Tests

```sh
npm run check
python tests/browser_e2e.py
python tests/remote_dom_smoke.py
```

The Node suite uses loopback HTTP and tests MCP routing, authentication, allowlisting, cancellation, timeouts, duplicate-result rejection, and navigation/inspect command sequencing. Both browser smoke tests use Chromium, not Safari. `remote_dom_smoke.py` mocks GM extension APIs; it is not an end-to-end network integration test. The optional `remote_browser_e2e.py` attempts a full network/browser loop but **cannot run in the current restricted environment**, where Chromium navigation fails with `ERR_BLOCKED_BY_ADMINISTRATOR`, including when requests are intercepted. Do not report it as passing.

## Release gate

Do **not** tell users the AI-driven iPad MVP is ready merely because the source and loopback tests pass. The minimum release proof requires deployment behind trusted HTTPS, connecting the user's actual eligible Claude account and iPad, and recording one complete real browser workflow as defined in PRODUCT_REQUIREMENTS.md.
